# 曆代字形查詢工具 · 可行性报告

> 目标：为古籍标注工作提供一个**纯前端、可离线**的字形查询工具，覆盖从甲骨文到今天各时代有代表性的书体；能自动过滤简繁与异体差异；所有字形素材的授权都可随仓分发。

---

## 一、结论

**纯前端可行，且已经做出来了。**

判定依据（均由本仓实测数据支撑，不是估算）：

| 判据 | 实测结果 | 结论 |
| --- | --- | --- |
| 有没有合法可用的古文字形源 | hanzi-glyphs-svg 提供 18.7 万条带出处的 SVG 字形，逐层 CC0-1.0 / CC BY 4.0 | ✅ 可用 |
| 能不能把 SVG 编译成字体 | 7 层全量编译成功，79,516 个字形实例；另有說文小篆 10,879 字、開元小篆 9,713 字 | ✅ 可行 |
| 字体体积能不能上 web | 45 层总量 223.0 MB / 1,541 片，但按 unicode-range 切片后，浏览器只下当前页真正用到的块（实测查 8 字 × 默认 13 层 = 86 片 / 12.1 MB 字形 + 6.9 MB 索引） | ✅ 可行 |
| 简繁/异体能自动归一 | 6,760 个等价类覆盖 13,644 字，18/18 自检通过 | ✅ 可行 |
| 是否需要后端 | 全部是静态文件，`file://` 双击即可运行 | ✅ 无后端 |
| 能不能反过来「以形查字」 | 13 层 65,980 字形离线压成 146 B/字 指纹（12.9 MB），浏览器内 L1 比对六万级字形仅数十毫秒；8/8 噪声样本排名第一 | ✅ 可行（见 4.8） |

**关于「以形查字」的边界**：本工具的主线是「**以字查形**」——你已经猜到或认出了某个字，用来核对它在各时代、各家刻法下的写法。另配一条反向通道「**以形查字**」（见 4.8）：给一张拓片或手绘笔画，在九个古文字层里按形状距离排出候选。它**不做自动释读**——不调用模型、不做 OCR、不猜字义，只给可解释的形状相似度排名，最终判断仍由人做。此前评估过公开数据训练的印章识别，实测 IoU 仅 0.13–0.35（噪声级），因此没有采用模型路线。完整循环是：**拓片 → 形状候选排名 → 拉出各层写法并排比对 → 人工确认／存疑／排除 → 导出台账**。这个循环本来一次要翻十几本书，现在几秒钟。

**怎么读这张表**：古文字层越古越稀，这是真实的——甲骨文总共认出约 4,500 个不同字，其中能和今天楷书对上号的更少。所以查一个常用字，甲骨层有三成概率没有；查一个罕见字，反而可能只有甲骨/金文有。这正是**必须把「未收录」如实显示出来**而不是回退到系统字体的原因——回退会让人误以为是真字形。

小篆是个例外：三层并存——`seal`（SVG 层）42.2%、`beishida`（說文小篆）55.2%、`shuowen-seal-kaiyuan`（開元小篆）73.2%；三层并集 **2,880 / 3,755 = 76.7%**（二级 61.6%、GBK 12,618），常用字基本齐了。这是全库唯一一处「同一书体多层叠加」，因为篆书正是印章与古籍题名里最容易认不出的字。

## 四、关键技术问题与解法

### 4.1 SVG → 字体：踩过的三个坑

1. **viewBox 极不统一**：从 `0 0 400 400` 到 `0 0 17 8` 到紧包围盒 `111.12 5.76 316.75 522.84` 都有。直接缩放会让同一个字在不同层里大小差几倍。解法：按**每个字形自己的包围盒**归一化——长边缩到 860 单位、中心对齐到 (500, 380)、y 轴取反。
2. **轮廓没闭合**：TrueType 要求每条轮廓闭合，而 SVG 路径普遍不写 `Z`。解法：自写 `AutoClosePen` 在每段轮廓末尾补 `closePath()`，否则字体渲染出锯齿或整字丢失。
3. **`TTGlyphPen.glyph()` 返回的 Glyph 没有 `xMin`**：直接读会 `AttributeError`，早期版本因此把所有字形判成 empty（built 0 chars）。必须先 `g.recalcBounds(None)`。

4. **退化轮廓把「主形」变成空白**：上游有少量记录其实是一条 2 点的折线，转成 TrueType 后面积为零，却仍然带一个「看起来正常」的包围盒（例如 `二` = `(70,196,930,564)`）。它会被当成主形写进 cmap，于是**整个字显示空白**，而真正的字形躺在 `ss01` 之后——页面看起来像「这层没有这个字」，极难察觉。解法：新增 `MinPathPen`，按子路径缓冲，**点数 <3 的轮廓直接丢弃**；如果一个轮廓都不剩，就返回 `None`，让主形顺延到下一个可用写法。验收不能只看包围盒，要用 canvas 统计墨迹像素或 `AreaPen` 量面积。修完后甲骨层 1,165 个原先空白的字恢复（代价是 11 个只有退化字形的字被剔除：兆匡币氣片畑番紟罔肜驪）。

另外 `fontTools.svgLib.path.parse_path` 在当前版本是**双参**签名 `parse_path(d, pen)`，不能只传一个 `d`。

还有一类「码位」坑：北师大说文小篆的 cmap 只有 platformID=3/platEncID=4（**Big5**），不是 Unicode，浏览器按字查不到。`scripts/import_legacy_font.py` 逐码 `decode('big5'→'big5hkscs'→'cp950')` 建表，重写 cmap 为 format 4 + format 12（含 platformID=0 子表），字形表原样保留；顺带领回 18,438 条码位——实测其中 7,559 条指向空轮廓，写 cmap 前用 `BoundsPen` 剔除，最终 10,879 字。

### 4.2 简繁 / 异体归一：这是用户明确要求的核心

`data/variants.json`（870 KB 原始 / **186 KB gzip**）由 `scripts/build_variants.py` 生成，数据来自 Unicode Unihan 18.0.0 与 OpenCC，纯用并查集：

- **强边**（`kSimplifiedVariant` / `kTraditionalVariant` / OpenCC 1:1）→ 合并成**等价类** `same`
- **弱边**（`kSemanticVariant` / `kZVariant` / `kSpecializedSemanticVariant`）→ 只进 `related`，**不合并**

结果：6,760 个等价类，覆盖 13,644 字。

自检 18/18 通过，且刻意**不**合并下列一简对多繁（它们只出现在 `related` 里）：

`后/後`、`余/餘`、`云/雲`、`里/裡/裏`、`干/乾/幹/榦`、`发/發/髮`、`台/臺/檯/颱`、`只/隻`、`系/係/繫`

前端用法极简单：`canon[ch] ?? ch` 拿到规范字，`same[canon]` 拿到全部等价写法；查询时先试用户原字，再试规范字，再试同组异体。

**关键细节（这条不做就等于没做归一化）**：命中之后**不是取第一个就结束**，而是把该层收过的同类字**全部并起来计数**。原因是上游数据本身就混着简繁——实测 `說` 的等价类是 `说 / 說 / 説`，而 `chu` 层同时收了 `说`（1 个写法）和 `說`（1 个写法），`qinwenzi` 只收 `說`（2 个写法），`seal` 只收 `說`（1 个）。如果按「第一个命中就返回」，输入 `说` 在楚文字层只会看到 1 个写法，`說` 的那个写法被白白丢掉。

合并后：输入 `说`，楚文字层显示「异写 2 种 · 主形（说）+ 异体 說」，并注明「源用字 說（本次输入作 说，属同字异体）」。**这正是用户要求过滤掉的「简体字体 / 繁体字体」差异**——不管这层按哪种收，界面都当同一个字展示。

同时，弱关联只提示不合并：输入 `干` 只查 `干` 本身，`乾 / 幹 / 榦` 出现在「相关字」里供点击跳转；`后/後`、`余/餘`、`云/雲`、`里/裡/裏`、`发/發/髮`、`台/臺/檯/颱`、`只/隻`、`系/係/繫` 同理。这样不会把「干」错误地当成「乾」。实测验证表见 `docs/variants-report.md`。

**这条对印章尤其重要**：很多印章用的是「說」「寶」「長」这类繁体/异体写法的本字，如果只按简体码位查会全部落空。

已知的归一缺口（写在 `docs/variants-report.md` 第 5 节）：`伪/偽/僞` 未合并、`叶/葉` 只进 related、`历/厤/曆/歷` 与 `饥/飢/饑` 被 Unihan 语义链合并（对字形查询友好，但不符合严格的一简对多繁口径）。

### 4.3 体积与按需加载

**45 个层全部切片，总量 223.0 MB WOFF2 / 1,541 片**，直接塞给浏览器是不可行的。

解法：`@font-face` + **`unicode-range` 分片**。

- 每层按「GB2312 一级 → 二级 → 其余按码位」排序，再按**字节预算**切块（不是按字数切——甲骨单字 1.5 KB，小篆 0.55 KB，按字数切会让甲骨块大 3 倍）。
- 每个分片写一条 `@font-face`，`unicode-range` 只列它真正包含的码位。
- 浏览器只在页面上真的出现某层需要的字时，才去下那块字体。

**实测**（不是估算）：打开工具查「永受嘉福長樂未央」8 个字、开默认 13 层（9 古文字 + 马善政/霞鹜文楷/志莽行书/刘建毛草——默认已改成楷行草各一），实际拉取 **86 片字体 = 12.1 MB**，外加 `layers.js` 1.86 MB + `variants.js` 0.83 MB + 这 13 层的元数据 4.18 MB（傳抄古文一层就占 2.4 MB）。合计 **18.9 MB**，之后每多查一个字通常只补 0–1 片。

对「本地双击打开」的用法这完全无感（读本地磁盘）；只有将来真要挂到服务器上时才需要再优化。优化路径已明确：**把分片顺序从「GB2312 拼音序」改成「字频序」**，让首页最常用的几百字挤进第 0–1 片，8 字查询就能从 86 片降到个位数——这一步只换排序键，不用重编译字形，属于纯增量改动。

用 `file://` 直接打开也不会因为 CORS 报错——因为数据不走 `fetch`，而是生成为 `window.GA_LAYERS` / `window.GA_VARIANTS` / `window.GA_META[层]` 的普通 `<script>`。

### 4.4 异写（同字多写法）

同一个字在甲骨/金文/楚简里往往有几十种写法，这是认字时最有用的信息。

编译时每个字保留最多 **9 种写法**（按出现频次），主形进 cmap，其余挂 GSUB 的 `ss01`–`ss08` 单替换特性。前端用 `font-feature-settings: "ss0N" 1` 切换——同一个字体文件、同一个字符，切换特性就能看到第 N 种写法，不用加载额外资源。

实测：甲骨 2,103 字摊到 11,807 个字形（平均 5.6 种写法），楚文字 11,187 / 4,173，隸書 12,352 / 5,679。

**浏览器实测通过**（这一步必须验，因为子集化很容易把 GSUB 剪掉）：`永` 在甲骨层 9 种写法，逐张点开后大字预览的 `font-feature-settings` 依次变成 `"ss01"`…`"ss08"`，且九个字形肉眼各不相同。切片器也逐层报告 `alt ok`（异写特性在子集中保留）。

每张写法卡片带**出处**：`甲2414 賓組`、`甲3333`、`乙749`、`鐵90.4`、`前4.11.3`、`佚37`、`佚460`——标注时要引哪一片甲骨，卡片上直接写了。

### 4.5 印章场景

工具内建「墨 / 朱文 / 白文」三种预览：朱文是白字红底（阳刻），白文是红字白底（阴刻），配合 210px 大字，可以直接和手里的钤印对照。

### 4.6 工程层面的坑（都踩过，都修好了）

纯前端的难点不在算法，在**静默失败**——错了不报错，只是结果少一半：

1. **生成的数据脚本语法错误，整层数据静默作废**。早期切片器把元数据写成 `window.(window.GA_META=window.GA_META||{})['seal']=...`（把一个表达式直接拼在 `window.` 后面），浏览器解析即失败，`<script onload>` 还会照常触发。表现是「异写永远只有 1 种、出处栏空白、点不开写法卡片」。修法：老老实实写 `window.GA_META['seal']={...}`，并把每个生成文件过一遍 `node --check`。
2. **异步数据到了，但结果没重算**。异写条数是算 `matchIn` 时从元数据里数出来的；元数据是 `onload` 后才有。只重画界面（`renderDetail()`）会拿着旧的结果画——明明有 9 种写法，界面写「1 种」。修法：元数据到位后跑整轮 `render()`（内部会 `computeMatches()`），并用 `metaAsked` 标记防自激循环。
3. **分批编译互相覆盖索引**。`build_glyph_fonts.py` 每跑一批就重写 `layers.json`，先编 seal 再编其余 6 层，seal 就从索引里消失了（前端少一整层且不报错）。修法：`make_layers_index.py` 从 `data/meta/*.json` + 成品 TTF 重新反推索引，与编译批次无关。
4. **两层字形设计框不一致，并排时一个字明显偏上、偏大**。实测 ‘開元小篆’ upem 1000 / ascent 880、bbox 中心 (242,500)；‘說文小篆’ upem 1024 / ascent 820、中心 (513,306)、长边比别层大 14%；SVG 编译层是 (500,380)/1000。修法：`scripts/normalize_glyphs.py` 逐字做刚性变换（长边 → `0.86*upem`、中心 → `(0.5*upem, 0.38*upem)`），并把 hhea / OS/2 的 ascent/descent 统一成 `0.88 / 0.12`。
5. **cmap 里有码位、字形却是空的**。北师大说文小篆 19,877 个 Big5 码位里 8,560 个是空轮廓占位符，转成 Unicode 后 7,559 条码位指向空字形；页面于是把字标成「有字形」却画成空白——比标「未收錄」更误导。修法：写 cmap 前用 `BoundsPen` 逐字形量 ink，空的直接不映射；同一方法也复核了全部 43 层。

### 4.7 部件检索：把「认字」变成「拆字」

真实场景是「只认得出半个字」——左边是 `氵`，右边不认识。这不需要图像识别，只需要一张**结构表**。

**数据源选型（两个候选，一个不收）**

| 候选 | 规模 | 许可 | 判断 |
| --- | --- | --- | --- |
| `cjkvi-ids` 的 `ids.txt` | 2.16 MB | README 明写衍生自 CHISE 项目，**GPLv2** | 不收：GPL 会传染到衍生数据 |
| **BabelStone IDS** | 3.29 MB / **97,680 条** / Unicode 16.0 / 2025-06-27 | 文件头写明「IDS 描述是事实，不受版权保护」「任何人可为个人或商业目的自由使用，无须请求许可、无须署名」，并放弃对呈现格式的版权主张、允许 fork 或作为新数据集的基础 | **采用** |

采用理由是许可最干净（近乎公有领域放弃），且条目最多（覆盖到 Ext-G/H/I）。只取「字 + IDS」两列，丢弃码位列与 `$(GKPTJ…)` 地区标记，**不改动任何序列内容**；许可原文摘录落在 `data/ids/LICENSE-IDS.txt`。

**解析**：标准 12 个 IDC（⿰⿱⿲⿳⿴⿵⿶⿷⿸⿹⿺⿻）＋ 2 个扩展（⿽ 包围右上、㇯ 减法）。97,680 条里 **95,536 条可完整解析**；余下 **2,144 条**用 `{nn}` 记无编码部件（`与 = ⿹{22}一`、`之 = ⿱丶{100}`）或带 `〾` 变化指示符——这些字仍能参与「任意位置」检索，但给不出确切方位，界面不假装知道。

**索引放在前端建，不预生成倒排表**：预生成会把同一批字重复存三遍（按部件、按方位、按位置），体积翻倍；改为切到「部件」标签时一次性解析 97,680 条，建「部件 → 方位 → 字串」索引（CJK 每字在字符串里只占 2 bytes），「任意」则直接线性扫 97,680 条 IDS 串。实测（Chrome，`file://` 本地磁盘）：

| 指标 | 实测 |
| --- | --- |
| `data/ids.js` | 1.69 MB（gzip 643 KB），只在切到该标签时加载一次 |
| 首次加载 + 建索引 | **< 60 ms** |
| 方位查询（左／右／上／下…） | **≈ 2–4 ms**（另有 30 ms 防抖） |
| 任意位置查询 | **≈ 7 ms** |

**语义与排序**：方位取「相对最近父节点」——`落 = ⿱艹洛`、`洛 = ⿰氵各`，所以 `氵` 在 `落` 里记为「左」，但不在根节点那一层；排序把根层命中的字排在前面，于是「左边是氵」既给出 `江 河 海`，也不漏 `落` 这类半嵌的。排序键＝「有几个已启用的字层收了这个字」→「GB2312 一级/二级」→ 码位，古籍用字天然靠前。

**实测样本**：`氵`＋左 = 1,194 字（河 游 酒 江 沈 洛…）；`皮`＋右 = 56 字（被 彼 波 披 破…）；`艹`＋上 = 1,172 字（若 葬 英 茅 荷…）；`口`＋任意 = 1,001 字（中 兄 古 可 台…）。另做常见异形部件归一：查 `氵` 同时查 `水`、`扌`↔`手`、`亻`↔`人`、`讠`↔`言`、`艹`↔`艸` 等。

**覆盖率**：34 个字层里，字体实际收录的字 **100% 都有 IDS 结构**（`beishida` 99.9%），所以点开任何一个查到的字，想知道它怎么拆，都有答案。

### 4.8 以形查字：把查询方向倒过来

前面所有功能都有同一个前提：**你得先猜出这是什么字**，才能查它长什么样。但古籍标注里真正卡住的恰恰是「连猜都猜不出」——尤其印章。这一节把方向倒过来：给一张拓片，问「哪些字长这样」。

**为什么不用模型**：公开数据训练的印章识别在实测里字形比对 IoU 只有 0.13–0.35，属噪声量级；而且纯前端跑 CNN 要拖几 MB 权重，还解释不了「为什么是这个字」。改用**可解释的形状距离**：每一步都能看见（二值掩膜、包围盒、密度指纹三个预览），参数全在用户手里。

**指纹设计**（`scripts/build_shape_index.py`，每字 **146 字节**）：

| 段 | 字节 | 内容 |
| --- | --- | --- |
| 密度网格 | 128 | 16×16，每格 4 bit（0–15），两格一字节 |
| 水平投影 | 8 | 16 行，每行 4 bit，按行最大值归一 |
| 垂直投影 | 8 | 16 列，同上 |
| 长宽比 | 1 | `clamp(w/h, .25, 4)` 线性映射到 0–255 |
| 墨量 | 1 | 掩膜内墨像素占比 |

归一化链：二值 → 紧包围盒裁切 → 等比缩放长边 56 → 居中进 64×64 → 4×4 盒式降采样成 16×16。
打分 `sim = 1 − (w·网格L1 + (1−w)·投影L1 + 0.10·长宽比差)`，`w` 是用户可调的「形状权重」。投影项让它对轻微形变鲁棒，网格项保住结构。

**踩到的最大的坑：JS 与 Python 必须逐位同构。** 最初前端用 `canvas.drawImage` + `imageSmoothingQuality="high"` 缩放，Python 用 `PIL Image.BOX`（面积平均）——两者不是同一个滤波器，同一个字自比对只有 88%，排名全乱。修法是前端手写 `boxResize()` 按覆盖面积加权，并把 5 处 `Math.round` 换成**四舍六入五取偶**的 `rint()`（对齐 Python `round()`）。改完自比对 100%，8 个内置样本与 Python 离线参考逐项吻合。

**验收**（8 个样本 = 真字形 + 高斯噪声/旋转/石花斑点/朱砂反色）：

| 样本 | 正确字 | 名次 | 相似度 |
| --- | --- | --- | --- |
| 小篆·永 | 永 | 1 | 98% |
| 小篆·福（磨蝕） | 福 | 1 | 91% |
| 甲骨·王 | 王 | 1 | 99% |
| 金文·受（旋轉） | 受 | 1 | 95% |
| 隸書·長 | 長 | 1 | 98% |
| 小篆·樂（朱文） | 樂 | 1 | 96% |
| 甲骨·日（斷裂） | 日 | 1 | 96% |
| 金文·央 | 央 | 1 | 96% |

**低分辨率输入（书影裁切、缩略图）怎么救。** 实测最常见的失败不是「认错字」而是「根本提不出墨」：一张 34×34 的裁切图，二值化后笔画只剩断点，再被默认去噪一腐蚀就整片消失。四步解决：

1. **先放大再二值化**。长边小于 240px 的图先用高质量插值放大（最多 8 倍），让反锯齿灰边变成可利用的亚像素信息；大于 400px 才缩。放大用的画布底色从黑改白——透明底 PNG 抠出来的字若是黑字，填黑会把它吃掉。
2. **自适应阈值**取代固定 128。取灰度直方图，背景峰取众数（紧裁切的单字图边框不可靠，不能用边框估计），墨峰取背景另一侧的次峰，阈值落在两峰中点；对比度过低（跨度 < 96）时先按 1%/99% 分位做拉伸。用户拖阈值滑杆即转为手动，勾选框可切回自动。
3. **去噪改成按连通域面积删斑点**，而不是统一做 3×3 开运算——开运算会顺带把 1px 细笔整条削掉。开运算改为「面积清理之后的补充一步」，且带墨量守卫：若开运算吃掉超过 45% 的墨，判定削过头，保留未开运算的掩膜。
4. **自动补救要有节制**。只有当墨量落入硬失败区（< 2% 或 > 60%）才尝试备选方案（自动反相、跳过去噪、加大放大），正常出墨时严格按用户参数走——早期版本只要质量分略低就自动改参数，反而把正确的样本改错。

「歸一化預覽」卡下方常驻一行诊断（`來源 34×34 · 工作 240×240（放大 7.1×） · 閾值 自動 69 · 對比拉伸 · 清斑點 −12`），图幅小于 32px 时额外提示「建議 ≥48×48」，让用户知道为什么没查到、该补什么。

实测：34×34 的小篆「永」放大 7.1 倍后查得 永 94% 排名 1；22×22 的「受」90%、「日」95% 排名 1；22×22 的「永」降到排名 2（88%）——22px 对篆书已是极限，工具会如实给出排名而不是假装确定。

**规模与性能**：13 层 65,980 字形 / 12.9 MB，按层懒加载（默认三层 3.0 MB）。比对在 `Uint8Array` 上直接算，不解码成对象：六万级字形只需数十毫秒。图片全程留在本机，不上传。

**它不是什么**：给的是形状排名，不是释读结论。16×16 分辨率会把说文里互为反文的 `永`／`𠂢` 压成同一指纹，两者并列第一是数据性质而非 bug。工具因此配了**标注台账**（确认／存疑／排除 + 笔记，localStorage 持久化，可导出 CSV/JSON），把「机器给候选、人做决定」这条线做实。

### 4.9 界面：为「看字形」这件事让路

纯前端工具没有后端可炫，界面唯一的职责是**让字形本身成为主体**。查询页与版权页因此重写成一套宋版書语言（`web/style.css`）：宣纸底纹（SVG `feTurbulence`，opacity .038）、界行分隔线、朱砂印泥色 `#9e2b1e`、主字预览内嵌米字格。以形查字页沿用同一套 token（`web/shape.css`），把卡片与结果区换成工作台布局：预览 canvas 里掩膜画成墨色、指纹热图从纸色过渡到朱砂；上传的拓片缩略图用 `filter:invert(1) + mix-blend-mode:multiply` 在纸面上还原成「墨字宣纸」，不必重渲染样本。

三处是为实际使用而非装饰做的：

| 改动 | 为什么 |
| --- | --- |
| 主字预览 200→232px、字形 144→168px，内置米字格 | 考释时要看清起收笔与重心；米字格给出结构参照，朱文态换成白色虚线 |
| 字形对照区加**小／中／大**三档（`localStorage['ga.cellsize']`） | 一次开 13 层要小图并排，研究一个字要大图。小档 48px 且隐藏时代行，大档 112px。只重绘矩阵，不重查 |
| ≤860px 把 36 个检索层折叠成开关 | 原先侧栏占满第一屏，查询框被推到 800px 以下——窄屏下工具根本没法用。折叠后查询框在 176px 处 |

两个真 bug 也在这轮修掉：`.sec-title` 类名在 CSS 里从来没定义过（章节标题一直是裸样式）；版权页当前导航项因 `nav a.strong` 与 `nav a.on` 特异性相同且后者在前，被覆盖成白字白底。

## 五、已知缺口（不掩饰）

1. **`seal`（SVG 小篆）层缺一批基本字**：`二`、`川`、`口` 在上游 CSV 里就没有（`口部` 收了 197 字但没有「口」本身，`川部` 收了 12 字但没有「川」）。这不是编译问题，也没法在本层补上。已由 `beishida` 与 `shuowen-seal-kaiyuan` 两层补上——三个篆体层同时开就不会缺，并集一级 76.7%。
2. **古文字层对常用字覆盖率 20%–78%**（见第三节）。查日常用字时甲骨层多半落空，这是数据的天花板，不是实现问题。
3. **隶书字体形态无干净来源**：唯一候选 wt021 因来源争议隔离（详见 2.4）；魏碑已由王漢宗 wts43 补上。
4. **以形查字只给形状排名，不做释读**：16×16 密度指纹会把互为反文的字压成同一指纹（永／𠂢 并列第一），残泐粘连需人工调参，最终判断必须由人做（详见 4.8）。形状索引只覆盖九个古文字层，现代刻本字形不参与反查。
5. 生僻字大量落在非 BMP 区（Ext-B 及以后，占 variants 数据的 35%），前端全部用 `Array.from` / `codePointAt` 处理，不会把代理对拆坏。

不需要服务器、不需要装任何东西。所有资源都在 `web/` 目录下，整个目录拷到 U 盘也能跑。

界面：

- 左上「仅古文字 / 全开 / 全关」切换层；点单层可以单独开关。
- 输入框支持**粘贴整段古籍原文**，会自动去重成字表，每个字显示在几层里有字形（绿点=有，红点=没有）。
- 单字详情：左边 210px 大字预览（可切墨/朱文/白文），右边是层、时代、授权、出处（「說文‧水部」「毛公鼎 集成2838 西周中期」「甲1066」这类）和异写条。
- **异写卡片**：每张一张写法，卡片下方标出处与 `主形/ss01…ss08`；点开即在大图里切换，同一字体文件、不额外加载。
- 「源用字」一栏会告诉你：你输入的字和这一层实际收的字不一样时差在哪（简繁/异体），并把这一层按不同字形收的全部写法合并计数。
- 底部「相关字」列出一简对多繁的弱关联字（如 `干 → 乾/幹`），点一下就能跳过去查。
- 顶部「部件檢索」标签：选方位（左／右／上／下／中／外／内／任意）＋部件（可从 28 个常用部件里点，或自己输入），反查所有符合结构的字；结果按「有几个字层收录」排序，点任意一格即切回查字模式看它的历代字形。
- 顶部「以形查字」标签：拖入拓片／印面截图（也可 Ctrl+V 粘贴、读剪贴簿、或直接在画布上手绘笔画）。左栏实时显示二值掩膜与 16×16 指纹，右栏给出候选排名；阈值、反相、去噪、笔画粗细、旋转、边框裁切、形状权重七个参数即时生效，调过会在控制台标出「已調：…」。点候选开抽屉看真实字形与出处，可标「确认／存疑／排除」并写笔记，台账存本机、可导出 CSV/JSON。查字页详情里的「以形反查此字」可直接把当前字送进来当样本。

## 附錄：印章考據（整幅書影找印、拆字、逐格查形）

全在浏览器里做，分四步：

1. **找印**：把像素按 HSV 拆开，取色相靠近朱砂（357.3°）、饱和度与明度在合理区间内的像素做掩膜，8 邻域膨胀后跑连通域。五项过滤（最短边、面积、密度、对比度）挡掉纸纹噪点；若某个连通域已被更大的印面包住 ≥85%，不再单独计数——否则朱文印「边框 + 框内互不相连的字」会被数成好几枚。
2. **取墨**：印面裁切后先按面积剔掉贴边的框线连通域，再从四边向内剥掉整行整列的墨（限幅 14–18%）。朱文取红度为墨；白文（红底白字）先求红底包围盒，只在该框内反相取字，否则四周白纸会被当成笔画、包围盒撑满整幅。
3. **拆字**：不用「找投影谷」那套——字形内部的笔画间隙也是谷，会把一个字切成碎笔画。改成按**墨列／墨行的连续段**切，并在切完后做合理性检查（每格宽高比落在 0.40–2.5，否则退回整幅一格）。字格顺序按右上起、直行右至左。
4. **查形**：每格掩膜走同一套归一化（紧包围盒 → 64×64 → 16×16 密度网格 + 双向投影），与索引做 L1 比对，逐格给出候选排名并可一键跳到该字详情页。

小印面复用 4.8 的放大链（长边不足先放大、阈值按时取），实测 44×252 的竖长印与 120×120 的朱文印都能正确切分。四张内置样本（永受／長樂未央／右司馬／福）分别切出 2／4／3／1 格，除「長」与「愽」几乎打平外全部 rank-1。
